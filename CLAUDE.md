# Aventura

Lightweight software 3D rendering engine, **100% pure Java, CPU only**: no GPU, no native code,
no third-party runtime library (only the JDK; JUnit 4 for tests). Java 21, Maven, MIT license.

## Guiding principles

- **Stay pure Java and CPU-based.** Never add a runtime dependency, JNI, OpenGL/GPU binding.
- **The project is didactic.** Favor readable code and recognizable algorithms over ultimate
  optimization. A performance gain that makes an algorithm hard to follow must be discussed first.
- Keep the public API stable unless the task is explicitly about changing it.
- Code, comments, Javadoc and docs are written in **English**. Exception: the two audits
  (`docs/PERFORMANCE_AUDIT.md`, `docs/JAVADOC_AUDIT.md`) also have a French version (`*.fr.md`) for
  Olivier. The English one is the reference; any change is made in both versions at the same time.

## Build, test, run

Two Maven modules under a parent `pom.xml`: run the commands from the project root, Maven builds the
engine then the demos.

- Compile: `mvn compile` (tests: `mvn test-compile`)
- Unit tests (JUnit 4, ~640, headless): `mvn test`
  - Single class: `mvn test -Dtest=TestMatrix4 -Dsurefire.failIfNoSpecifiedTests=false`
  - One module: `mvn test -pl aventura-engine` (`-pl aventura-demos -am` also builds the engine)
- Run a demo or a visual test program (only `aventura-demos` runs it; textures come from the classpath):
  `mvn test-compile exec:java -Dexec.mainClass=com.aventura.demo.AventuraDemo`
- Javadoc of the engine: `mvn javadoc:javadoc` (output in `aventura-engine/target/reports/apidocs`)
- Always run `mvn test` before declaring a change done. Visual test programs
  (`com.aventura.test.*`) open windows: do not launch them unless asked, Olivier checks them by eye.

## Layout

- `pom.xml` parent (packaging `pom`): modules, shared versions and plugins
- `aventura-engine/` the engine, **no dependency but the JDK**, never depends on the demos
  - `src/main/java/com/aventura/`
    - `math/` vectors, matrices, quaternions, transforms, projections, tools
    - `model/` world, elements and shapes, camera, lights, materials, textures, perspective
    - `engine/` rendering pipeline, rasterization, fragments, shadow maps
    - `context/` graphic and rendering contexts
    - `view/` `GUIView`, `ImageView`, `SwingView`, `MapView`
    - `tools/` color, tracing
  - `src/test/java/com/aventura/` unit tests mirroring the main packages (`src/test/resources`: a texture)
- `aventura-demos/` depends on the engine
  - `src/main/java/com/aventura/demo/` demo applications (`temple/`: the `TempleRuins` demo, `ship/`: the
    `StarshipInterior` demo), and what the demos share: `DemoTextures`, `StatisticsWindow`, `FrameTimeStatistics`,
    `LightBudget`, `Noise`, `FlightPath`
  - `src/main/resources/texture/` the textures, read from the classpath (`DemoTextures.url("name.jpg")`)
  - `src/test/java/com/aventura/` `demo/` tests of the demos, `SceneViewer`, `PerfBench`,
    `DocumentationImages`; `test/` ~80 visual test programs with a `main()`; `cookbook/` the Geometry and
    Atmosphere Cookbook examples and their tests
- `docs/images` documentation images (regenerated by `DocumentationImages`)
- `docs/`
  - `BACKLOG.md` work items not handled yet (read it when picking or finishing a backlog item)
  - `DESIGN.md` architecture, pipeline, lighting, shadows, contexts, conventions
  - `TEMPLE_RUINS.md` the making of the `TempleRuins` demo: architecture, graphic design, tricks, UI,
    limitations, performance (update it when the demo changes)
  - `STARSHIP_INTERIOR.md` the making of the `StarshipInterior` demo, on the same model (update it when the demo
    changes)
  - `GEOMETRY_COOKBOOK.md`, `ATMOSPHERE_COOKBOOK.md`, `PERFORMANCE_AUDIT.md`, `JAVADOC_AUDIT.md`
    (the two audits with a French version `*.fr.md`, kept in step)

## Conventions (see docs/DESIGN.md §12)

- **Z is up.** Cameras use `Vector4.zAxis()` as up vector.
- Directional lights are defined by their **propagation direction** (light towards scene).
- New shapes extend `GenerativeElement`, not `Element`.
- Never retain a `Fragment` (or its vectors) after `consume()` returns; copy values out.
- Transform order is S → R → T (`M = T · R · S`), composed parent-first down the tree.
- Refresh, don't cache: derived matrices go through `ViewProjection.refresh()` once per frame.
- Tests must run headless (Surefire sets `-Djava.awt.headless=true`).
- Constructor argument order differs between `PerspectiveContext` and `Perspective`/`Projection`
  (see BACKLOG §1): double-check before calling them.
